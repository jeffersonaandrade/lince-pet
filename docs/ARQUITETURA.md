# Arquitetura Lince Pet (Next.js fullstack)

O backend AdonisJS (`Lince-Pet-Backend-main`) foi migrado para Route Handlers do Next.js neste repositório. O contrato HTTP (paths, JSON, status e mensagens) é o mesmo do Adonis, então o frontend não mudou além da autenticação.

## Camadas

| Camada | Onde | Regra |
|---|---|---|
| Rotas HTTP | `src/app/api/**/route.ts` | Sempre `route()` + `ApiRequest.from()` + `requireUser()`; responder com `ok/created/...` de `src/server/http.ts` |
| Infra HTTP | `src/server/http.ts` | `handleError` reproduz o exception handler do Adonis (422 VineJS, `HttpError`, 500 genérico); `json()` serializa como o Lucid |
| Compatibilidade Lucid | `src/server/lucid.ts` | `creating()`/`updating()` (UUID e timestamps não têm default no schema), `paginate()`, `serialize()` |
| Auth | `src/server/auth/*` | JWT HS256 com `APP_KEY` (7 dias, `typ: JWT`, `jti` e versão `tv`) no cookie httpOnly `auth_token`; senha scrypt no formato PHC do Adonis; `requireUser(req, [tipos])` = middlewares jwtAuth + userType |
| Domínio | `src/server/services/*` | Asaas, storage de imagens (Supabase Storage), e-mail (Resend), WhatsApp, Google Calendar, notificações in-app, limites de plano, onboarding |
| Validação | `src/server/validators/*` | VineJS v3 (mesmas mensagens do backend antigo) |
| E-mails | `src/server/emails/*` | Templates Edge convertidos em funções TS que retornam HTML |
| Banco | `prisma/schema.prisma` + `prisma.config.ts` + `src/server/db.ts` | PostgreSQL (local via Docker ou Supabase); Prisma 7 com `@prisma/adapter-pg`, client gerado em `src/generated/prisma` (importar de `@/generated/prisma/client`); singleton com `omit` global de senha e tokens Google |

Todo arquivo em `src/server` começa com `import 'server-only'`.

## Convenções herdadas do banco

- Booleanos são `Int` (0/1): o frontend compara com `0`/`1` (ex.: `onboardingComplete === 0`).
- ENUMs do Postgres (`user_type`, `genero`, `tipo_clinica`, `porte`, `payments.type`) são enums do Prisma. Como `String`, a leitura no banco real falha com P2032.
- Conexão: `DATABASE_URL` e `DIRECT_URL` são iguais. No `.env` (dev e Prisma local) apontam para `127.0.0.1:5433`. No `.env.production` (`next build` / `next start`) apontam para o pooler do Supabase em modo sessão, porta 5432 do host `aws-0-us-east-2.pooler.supabase.com`. A conexão direta `db.<ref>.supabase.co` é só IPv6. A app autentica com o próprio JWT; usa o usuário `postgres` do banco, não a chave anon. O Migrate lê `DIRECT_URL` no `prisma.config.ts` (com `dotenv/config`, que não sobrescreve o ambiente). A app conecta pelo `DATABASE_URL` com a config de `src/server/db-conexao.ts`: pool `max: 5`, `connectionTimeoutMillis: 5000` (o `pg` não tem timeout por padrão) e, em host `*.supabase.com`/`*.supabase.co`, `ssl: { ca: SUPABASE_CA, rejectUnauthorized: true }`, tirando `sslmode` da URL (no `pg`, os parâmetros da URL sobrescrevem a opção `ssl`). O pooler assina com a "Supabase Root 2021 CA" (vence em 26/04/2031): sem ela, o handshake falha com `SELF_SIGNED_CERT_IN_CHAIN`. Nunca usar `rejectUnauthorized: false`.
- **API REST do Supabase fechada:** a migration `20261015200000_enable_rls_public_tables` ativa RLS (sem policies) em todas as tabelas de `public` e revoga `anon`/`authenticated` (inclusive para tabelas futuras, via `ALTER DEFAULT PRIVILEGES`). Aplicada em produção via MCP em 15/10/2026 (36/36 tabelas); o próximo `migrate deploy` reexecuta (idempotente) e só registra em `_prisma_migrations`. O Prisma conecta como `postgres` (dono das tabelas, `bypassrls`) e não é afetado. Rollback: no mesmo laço, `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` e `GRANT ALL ... TO anon, authenticated`. Conferência: `get_advisors` (security) sem `rls_disabled_in_public` e `begin; set local role anon; select count(*) from public.users; rollback;` precisa dar "permission denied".
- **Supabase via MCP:** operações no projeto Supabase seguem `.cursor/rules/supabase-mcp.mdc` (leitura livre; DDL com plano aprovado; DML/destrutivo em produção só com confirmação explícita).
- Busca textual em SQL cru usa `ILIKE` (o Postgres diferencia maiúsculas); no Prisma, `contains` sempre com `mode: 'insensitive'`. Login e “esqueci a senha” também comparam e-mail sem diferenciar maiúsculas. O índice único de `users.email` diferencia: o cadastro grava o e-mail em minúsculas.
- `User -> tutor/veterinario/clinica/prestador` são listas no Prisma (`user_id` sem UNIQUE): usar `findFirst({ where: { userId } })`.
- DECIMAL sai como string com 2 casas; datas saem em ISO (servidor em `TZ=UTC`).
- `agendamentos.data_consulta` é VARCHAR (`YYYY-MM-DD`).
- Migrations: Prisma Migrate com baseline `prisma/migrations/0_init`. `docker compose up` sobe o Postgres local e aplica as migrations pendentes; não roda o seed (`npm run db:seed` é separado). `npm start` aplica as migrations do `.env.production` (Supabase) e só então sobe o Next. Em banco que já existia antes do Prisma: `prisma migrate resolve --applied 0_init` uma única vez.
- Dados do MySQL antigo: `npm run db:migrar-mysql` (`scripts/migrar-dados-mysql.ts`) lê `MYSQL_ORIGEM_URL` e copia para o `DATABASE_URL` (`--env=.env.production` para o Supabase). Sem `--executar` só confere: tabelas e colunas de cada lado, contagens e bloqueios (coluna NOT NULL sem default ausente no MySQL). Com `--executar`: copia as colunas em comum na ordem das FKs, numa única transação (erro = nada gravado), com `ON CONFLICT DO NOTHING`, ajusta as sequências autoincrement e confere as contagens. Rodar com o destino recém-migrado e **antes** do seed (o seed é idempotente e completa o catálogo depois). Tabelas do Adonis (`adonis_schema*`) ficam de fora; datas `0000-00-00` viram NULL; datas são lidas em UTC.

## Fluxos principais

- **Capacidade para o admin:** `/admin/uso`, acessível pela navegação de `/admin/aprovacoes`, acompanha o banco conectado e os arquivos do Storage. Página e `GET /api/admin/capacidade` revalidam `requireAdmin`; visitante vai ao login e usuário comum não consulta métricas. Banco: `pg_database_size(current_database())` e 15 maiores tabelas de todos os schemas, com índices e contagem estimada por `pg_stat_user_tables`. Arquivos: soma dos tamanhos em `storage.objects.metadata`, separada por bucket; ausência de schema/permissão/timeout não vira uso zero. Consultas em transações somente leitura, `statement_timeout` de 3 s; cache agregado de 60 s por instância e deduplicação de chamadas simultâneas. Referências padrão de 500 MB / 1 GB, ajustáveis em `ADMIN_CAPACIDADE_BANCO_MB` / `ADMIN_CAPACIDADE_STORAGE_GB`, sem alterar o plano contratado. Alertas a 70%, 90% e 100%. Sem histórico não se estima data de esgotamento. Cobrança/egress, WAL, CPU, conexões e outros projetos precisam ser conferidos no painel Supabase. Detalhes em `docs/ADMIN-CAPACIDADE.md`.

- **Correções da auditoria (23/10/2026):** rastreabilidade dos 23 itens e pendências em `docs/CORRECOES-AUDITORIA-SEGURANCA.md`. Login Google de uma conta ainda não verificada substitui a senha por segredo aleatório, comprova o e-mail, revoga sessões por `token_version` e remove resets anteriores na mesma transação. Quem quiser voltar a entrar por senha deve usar a recuperação por e-mail. Reset de senha exige 8–255 caracteres, consome o token atomicamente e revoga as sessões anteriores.
- **Decisões de aprovação:** a listagem inclui fingerprint do CRMV/RT e de `updated_at`. O POST deve enviar esse fingerprint em `revisao`; dados alterados geram 409. A gravação também compara o estado revisado para impedir troca entre a leitura e a aprovação. O fingerprint inclui os dados porque `updated_at` tem resolução de segundos.
- **Agenda e início:** criação e remarcação usam advisory lock transacional por veterinário/prestador. Consultas veterinárias aceitam horário estrito `HH:mm`. A validação do código de início é serializada por agendamento, inclusive o incremento de tentativas inválidas. Trocar plano preserva o contador mensal; somente a renovação mensal deve reiniciá-lo.
- **Push e perfis:** endpoints push são limitados aos provedores permitidos, inclusive no envio de inscrições antigas; até 10 aparelhos por usuário e timeout de 5 s por envio. Experiências: até 30, descrição até 5.000 caracteres, troca transacional com lock por veterinário. Horários da clínica: JSON até 10.000 caracteres na gravação. Esses limites não saneiam automaticamente dados antigos.
- **Seed:** `npm run db:seed` popula o catálogo. As contas demo exigem `SEED_DEMO=true` e são proibidas com `NODE_ENV=production`. O setup e2e habilita explicitamente o demo depois de conferir que o banco é local. Não usar esse opt-in com banco compartilhado ou de produção; a trava não detecta a finalidade de um banco apenas pelo hostname.

- **Login:** `POST /api/auth/login` grava o cookie `auth_token`; `GET /api/auth/me` devolve o usuário; o frontend não guarda token. O token só é lido do cookie ou do header `Authorization: Bearer`, nunca da query string ou do corpo. E-mail de login, recuperação de senha e Google é comparado sem maiúsculas, mas de forma exata (`findUserByEmail`: `%` e `_` não funcionam como curinga).
- **Sessão:** o token vale 7 dias. Redefinir a senha sobe `users.token_version` e derruba todas as sessões abertas (token com `tv` diferente = 401 "Sessão encerrada"; token antigo sem `tv` conta como 0). Logout grava o `jti` em `sessoes_revogadas` até a expiração do token e encerra só aquela sessão; linhas vencidas são apagadas no próximo logout. JWT de outro tipo assinado com a mesma `APP_KEY` (state do Google Agenda, `typ: google-calendar-state`) não vale como sessão.
- **Limite de tentativas:** por IP, em memória (vale por instância do servidor): login 10 / 15 min; esqueci e redefinir senha 5 / 15 min; cadastros (tutor, clínica, vet, prestador) 10 / 1 h. Acima disso, 429.
- **Tamanho do corpo:** `ApiRequest.from` recusa com 413 corpo acima de 6 MB (pelo `content-length` ou contando o que lê), antes de autenticar.
- **Cabeçalhos:** `next.config.ts` envia HSTS, `X-Frame-Options: DENY` + `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy` e `Permissions-Policy` (só geolocalização, usada na busca) em todas as rotas, sem `X-Powered-By`.
- **Health check:** `GET`/`HEAD /api/health` é público, sem cache, e roda `SELECT 1` com limite de 3 s: 200 `{status:'ok'}` ou 503 `{status:'erro'}` (detalhe só no log). O UptimeRobot chama a cada 5 min, o que mantém o Render gratuito acordado (ele hiberna após 15 min sem tráfego), mantém o Supabase gratuito ativo e avisa por e-mail se app ou banco caírem. Um serviço gratuito ligado o mês todo usa ~744 das 750 h do workspace no Render.
- **SSL com o Supabase:** a conexão da app com o Supabase sempre verifica o certificado com a CA do Supabase (`src/server/db-conexao.ts`), nunca com `rejectUnauthorized: false`. Quando a CA vencer (26/04/2031) ou o Supabase trocar, atualizar `SUPABASE_CA` com o arquivo de Database Settings > SSL Configuration.
- **Limpeza de texto:** `ApiRequest` tira os espaços das bordas de todo texto do corpo (JSON e formulário) e texto vazio vira `null`; na query string só tira as bordas (`?q=` continua `''`). Campos com `senha` ou `password` no nome passam intactos. Espaços e quebras de linha no meio do texto ficam.
- **Parser de requisição:** `ApiRequest` ignora chaves `__proto__`, `constructor` e `prototype` na query e em formulários (evita poluir `Object.prototype` do processo) e só lê campos próprios do objeto.
- **Google:** login social em `/api/auth/google/*` (state em cookie; só aceita conta Google com `email_verified`) e Calendar em `/api/google/calendar/*` (state JWT + sessão do navegador).
- **Agendamento:** `POST /api/agendamentos` só aceita `clinica_id` de clínica com vínculo `aceito` com o vet (senão 400); endereço do vet ligado a uma clínica sem vínculo aceito não dá à clínica a consulta. Checa limite do plano, grava, notifica (in-app; e-mail e WhatsApp conforme "Canais de aviso e Google Agenda") e cria evento no Google Agenda via `after()`.
- **Assinaturas:** `/api/assinaturas/*` são wrappers finos de `src/server/services/assinaturas.ts` (contratar, trocar, cancelar), que cria/cancela no Asaas; `POST /api/webhooks/asaas` é idempotente via `webhook_events.event_id` e é quem aplica plano/status (ver "Assinatura").
- **Uploads:** multipart -> `UploadedFile` (tamanho/extensão) -> `src/server/services/storage.ts` (sharp + Supabase Storage) -> URL pública gravada no banco. Detalhes em "Storage de imagens".
- **Agenda:** a grade semanal fica em `veterinario_enderecos.horarios_funcionamento` (presencial) e `veterinarios.horarios_online`, editada no Perfil. `PUT /api/veterinarios/profile` não altera dono (`veterinario_id`), clínica (`clinica_id`), id nem foto do endereço principal: esses campos são ignorados (foto tem upload próprio; clínica só por vínculo aceito). Bloqueios pontuais ficam em `bloqueios_agenda` (`src/server/services/bloqueios.ts`). `GET /api/agendamentos/disponibilidade/:vet` devolve `horarios_ocupados` (consultas + bloqueios), `horarios_bloqueados` e `dia_bloqueado`.

## Regras de negócio

Toda decisão de negócio nova entra aqui e no grafo do graphify (ver `.cursor/rules/graphify.mdc`).

### Entrega e versionamento

- **Commit e push direto na main autorizados:** autorização do usuário registrada em 23/10/2026, válida para os trabalhos autorizados deste projeto enquanto não for revogada. Ao finalizar, executar as verificações pertinentes, commitar as alterações e fazer push diretamente em `main`, sem pedir nova confirmação para essas ações. Atualizar as referências do remoto e integrar alterações existentes antes do push, preservando o histórico e o trabalho de outras pessoas; não usar force-push. Informar o commit enviado e os resultados ou pendências da validação. A autorização de versionamento não amplia o escopo da tarefa nem equivale a confirmar que o deploy em produção terminou.

### Bloqueio pontual de agenda

- **Grade semanal x bloqueio pontual:** a grade semanal é recorrente e não é alterada pelo bloqueio. O bloqueio vale só para as datas informadas (bloquear 15/10 não afeta 22/10).
- **Diário ou período (pontual):** um bloqueio tem `data_inicio`/`data_fim` (`YYYY-MM-DD`, até 31 dias, sem datas passadas). `horarios = null` bloqueia o dia inteiro; uma lista `HH:mm` bloqueia só esses horários em cada dia do período.
- **Recorrente (toda semana):** `recorrente = 1` + `dias_semana` (0=domingo) repete o bloqueio nesses dias a partir de `data_inicio`; `data_fim` é opcional (null = até o profissional remover) e não tem limite de 31 dias. Serve para "toda quinta só atendo de manhã" sem mexer na grade do Perfil.
- **Intervalo de horários:** no modal, "Das/Até" marca de uma vez todos os horários de 30 min do intervalo (fim exclusivo: 11:00–17:00 bloqueia 11:00 a 16:30). Assim o vet fecha 3–5 horas e atende só no restante do dia.
- **Quem bloqueia:** o veterinário (`/api/veterinarios/bloqueios`) e a clínica com vínculo `aceito` (`/api/clinicas/veterinarios/:vet/bloqueios`, `DELETE /api/clinicas/bloqueios/:id`). Sem vínculo aceito: 404.
- **Consultas no período:** o front chama `POST ...?preview=1` e mostra as consultas `pendente`/`confirmado` afetadas. Ao confirmar, elas são canceladas com motivo "Agenda bloqueada pelo profissional", o uso mensal do vet é devolvido e o tutor é avisado (in-app + e-mail).
- **Sem estorno automático:** consulta paga cancelada pelo bloqueio é estornada manualmente.
- **Vale para todos os locais:** o bloqueio é do veterinário, não do endereço (presencial e online).
- **Remover bloqueio** libera os horários, mas não restaura consultas canceladas.
- **Trava no backend:** `POST /api/agendamentos` e `PATCH /api/agendamentos/:id/reagendar` recusam horário bloqueado (400).

### Anotações privadas do veterinário

- **Visibilidade:** a anotação (`agendamento_anotacoes`, 1:1 com a consulta) é lida/editada só pelo veterinário dono em `GET/PUT /api/veterinarios/agendamentos/:id/anotacao` (outro vet: 404). Fica em tabela separada e nenhuma rota de tutor ou clínica a inclui.
- **Quando pode:** a partir do início do atendimento (`started_at` preenchido, status "em andamento") e depois de concluída, sem prazo para editar. Pendente, confirmada ou cancelada: 400.
- **Campos:** local do atendimento (endereços do vet, Online, Domicílio ou texto livre), status do pagamento (`pago`/`pendente`/`isento`), forma (`pix`/`cartao`/`dinheiro`/`plano_pet`/`outro`), nome do plano (só com `plano_pet`) e observações do paciente (até 5.000 caracteres).
- **Não altera pagamento real:** os campos de pagamento são registro do vet; `payment_status` da consulta e o Asaas não mudam.
- **Histórico por pet:** no modal da consulta (qualquer status, exceto cancelada) o vet abre o histórico do pet: `GET /api/veterinarios/agendamentos/:id/anotacao/historico` devolve só as anotações **dele** em outras consultas do mesmo pet, mais recentes primeiro. Anotações de outros veterinários nunca aparecem.

### Prontuário do pet

- **Registro clínico por consulta** (`registros_clinicos`, 1:1 com a consulta): queixa, diagnóstico, tratamento/prescrição, peso (0 a 500 kg), vacinas/medicações aplicadas, retorno sugerido (hoje ou futuro), plano de saúde usado e encaminhamento em texto livre. Textos com até 5000 caracteres.
- **Autor:** só o vet da consulta escreve (`GET/PUT /api/veterinarios/agendamentos/:id/registro`), com a mesma janela da anotação privada: a partir do início do atendimento, editável depois de concluída; consulta cancelada não tem registro.
- **Acesso ao prontuário** (`GET /api/pets/:id/prontuario`): o tutor dono e qualquer vet ou clínica com consulta **não cancelada** do pet (inclusive futura, para se preparar; confirmado pela dona do produto) veem o prontuário inteiro, com registros de outros profissionais. Demais usuários recebem 404.
- **Tutor vê tudo:** todos os registros clínicos aparecem para o tutor dono, sem marcação de compartilhamento.
- **Sem nota privada:** o prontuário nunca inclui a anotação privada (`agendamento_anotacoes`). O plano registrado na anotação é dado financeiro do vet; o plano clínico fica no registro.
- **Pet novo:** começa com o prontuário vazio e acumula uma entrada por consulta não cancelada.

### Equipe da clínica

- **Lista:** `GET /api/clinicas/professionals` e `GET /api/veterinarios` (clínica) devolvem os veterinários com vínculo `aceito` (`src/server/services/clinica-equipe.ts`).
- **Remover = desfazer vínculo:** `DELETE /api/clinicas/professionals/:id` e `DELETE /api/veterinarios/:id` apagam só o vínculo com aquele veterinário. A conta, as consultas e o histórico do veterinário permanecem. Sem vínculo: 404.
- **Limite de veterinários:** ver "Assinatura".

- **Provedor único:** Asaas (conta existente). Documentação consultada pelo MCP do Asaas (`.cursor/mcp.json`, `https://docs.asaas.com/mcp`). Regras puras em `src/server/services/assinatura-regras.ts`, fluxo em `src/server/services/assinaturas.ts`, eventos em `src/server/services/asaas-webhook.ts`.
- **Credencial com escape:** `AsaasService` remove aspas/espaços externos e barras de escape iniciais antes do `$` da chave, preservando o restante. O `.env` local tinha escape duplicado; antes da correção de 24/10/2026, a autenticação retornava 401. Não registrar a chave completa em logs nem no repositório.
- **Homologação em 24/10/2026:** [relatório e evidências](HOMOLOGACAO-ASAAS-2026-10-24.md). Ciclos sandbox de veterinário, clínica e prestador, boleto, Pix, cartão aprovado/recusado, inadimplência, estorno e webhooks reais passaram. Foi confirmado um bloqueador para produção: cancelamento pode responder sucesso local enquanto o Asaas mantém a assinatura ativa após erro remoto. O log bruto da falha Axios também inclui o header de credencial (confirmado com chave deliberadamente inválida). A correção posterior desses quatro pontos passou por regressão real no sandbox, incluindo recuperação de 401, upgrade e concorrência; ver [correção do cancelamento](CORRECAO-CANCELAMENTO-ASAAS-2026-10-24.md). Validar deploy, cron e configuração definitiva antes de produção. O webhook antigo do sandbox está desativado e aponta ao Railway antigo; o teste usou um webhook temporário, não a configuração definitiva do deploy.
- **Catálogo:** veterinário `vet_starter` (R$ 39,90) e `vet_pro` (R$ 59,90, módulo financeiro); clínica `starter` Pequena (R$ 99,90, até 5 vets), `clinic` Média (R$ 149,90, até 15 vets), `clinic_pro` Grande (R$ 219,90, ilimitado); prestador `free`/`pro`. Cada tipo só contrata os planos dele. Assinaturas já existentes no Asaas mantêm o valor antigo. Produção alinhada ao `prisma/catalogo.ts` em 15/10/2026 (upsert por `code` via MCP, ids preservados).
- **Sem plano:** veterinário e clínica começam em `none` e não têm os recursos pagos até assinar. Prestador começa em `free`.
- **Cortesia (contas anteriores ao Asaas):** contas que já tinham plano pago antes da cobrança pelo Asaas, sem nenhuma assinatura (em 15/10/2026: 1 veterinário `pro` e 1 clínica `clinic`), mantêm o plano como cortesia. Não são rebaixadas por script; perdem a cortesia só se assinarem/trocarem pelo fluxo normal. Contas novas seguem "Sem plano".
- **Cobrança:** fatura do Asaas com `billingType UNDEFINED` (o usuário escolhe Pix, boleto ou cartão na fatura), sempre mensal. A plataforma não coleta cartão.
- **Teste grátis:** 14 dias, sem cartão, só na primeira assinatura paga (dono sem nenhuma assinatura com `asaasSubscriptionId`). O plano ativa na hora e a primeira fatura vence no 14º dia. Sem pagamento, vira inadimplente e perde o plano.
- **Plano só muda após pagamento:** fora do teste, contratar ou trocar cria a assinatura `pending` e devolve o link da fatura; o plano só é aplicado em `PAYMENT_CONFIRMED`/`PAYMENT_RECEIVED`. Ao ativar, as outras assinaturas do mesmo dono são canceladas (Asaas e local). Assinatura cancelada/expirada ignora pagamento atrasado.
- **Status:** `active` = ativa, `pending` = pendente, `past_due` = inadimplente, `canceled`/`expired` = cancelada. `GET /api/assinaturas/status` devolve o rótulo, fim do teste, troca pendente e o link da fatura em aberto.
- **Inadimplência:** `PAYMENT_OVERDUE`, `PAYMENT_REFUNDED`, `PAYMENT_CHARGEBACK_REQUESTED` e `PAYMENT_RECEIVED_IN_CASH_UNDONE` marcam `past_due` e devolvem o dono ao plano padrão, salvo se ele tiver outra assinatura ativa. Pagar a fatura reativa.
- **Cancelamento confirmado:** o pedido é gravado em `asaas_cancelamentos` antes da chamada remota. Só `deleted=true` da assinatura correta (consulta/DELETE) ou webhook autenticado `SUBSCRIPTION_DELETED`/`SUBSCRIPTION_INACTIVATED` permitem marcar `canceled` e rebaixar ao padrão, sem período restante e sem estorno automático; outra assinatura ativa preserva o plano novo. Erro, timeout, 404 ou resposta incompleta mantêm a pendência e não anunciam sucesso. DELETE retorna 202 enquanto pendente e 200 após confirmação. O plano atual permanece até confirmar, salvo inadimplência comprovada. Trocar para `none`/plano grátis solicita o mesmo cancelamento.
- **Reconciliação de cancelamento:** fila persistente com lease de 2 minutos, até três trabalhos por execução, chamadas HTTP fora da transação e backoff de 1 minuto até 1 hora. Consulta remota antes do DELETE reconcilia respostas perdidas. Webhook e worker finalizam atomicamente sob lock do assinante. O cron existente `/api/cron/lembretes-whatsapp` também drena a fila; `/api/cron/assinaturas` permite execução dedicada com o mesmo `CRON_SECRET`. Tentativas dependem de cron funcionando; falhas persistentes exigem intervenção pelo código seguro registrado nos logs/banco.
- **Troca e cancelamento:** ao confirmar o plano novo, o webhook enfileira cancelamento das antigas e marca `cancel_pending`, sem bloquear sua transação com HTTP. Elas deixam de conceder acesso, mas a obrigação de cancelá-las permanece até confirmação remota. Nova contratação/troca fica bloqueada (409) enquanto houver cancelamento pendente. Pagamento tardio de assinatura com pedido de cancelamento não reativa o plano e não gera estorno automático. Durante a pendência remota ainda pode haver cobrança pelo provedor.
- **Interface de assinatura:** veterinário, clínica e prestador podem solicitar cancelamento e retomar a mesma fatura aberta. Durante cancelamento pendente, a tela não oferece a fatura em encerramento, exibe aviso explícito e consulta o status a cada 10 segundos; atualizar a tela não substitui a execução do cron. Cancelamento exige confirmação do usuário na interface.
- **Logs Asaas:** somente código controlado (`HTTP_nnn`, `TIMEOUT`, `ERRO_INTEGRACAO`), status HTTP e identificador interno de assinatura; nunca serializar erro Axios, corpo do provedor, headers, mensagem arbitrária, dados pessoais nem fragmentos da credencial. Payload do webhook permanece no registro interno existente para idempotência; não é impresso em logs.
- **Limite de vets da clínica:** convite (`POST /api/clinicas/professionals`) e aceite de vínculo contam vínculos `aceito` + `pendente`; acima de `maxVeterinarios` ou sem plano pago: 403. Vínculos já existentes não são desfeitos.
- **Webhook:** `asaas-access-token` precisa bater com `ASAAS_WEBHOOK_TOKEN` (comparação em tempo constante); com o app em produção ou `ASAAS_ENV=production` o token é obrigatório (sem ele, 401). Erro interno responde 500 sem detalhes. Eventos repetidos são ignorados por `webhook_events.event_id`.
- **Busca de veterinários:** não filtra mais por créditos; `vet_pro` aparece antes de `vet_starter`.

### Notificações por WhatsApp

- **Número central:** todas as mensagens saem de um único número da Lince Pet, que distribui avisos para tutores, vets e clínicas. Vet e clínica não conectam número próprio.
- **Provedor agnóstico:** `src/server/services/whatsapp.ts` define `WhatsAppProvider` e escolhe o driver por `WHATSAPP_PROVIDER` (padrão `log`, que só registra). Trocar de provedor (Z-API, UltraMsg, Evolution...) = novo driver, sem mexer nos fluxos. Provedores não oficiais têm risco de banimento do número.
- **Eventos e destinatários:** confirmação (tutor) e novo agendamento (profissional) na criação; lembretes 24h e 2h antes (tutor); cancelamento pelo tutor (profissional); cancelamento por bloqueio de agenda (tutor, com o motivo); remarcação (tutor e profissional). Profissional = celular do vet, ou o WhatsApp da clínica se o vet não tiver celular.
- **Sem texto livre do tutor:** ao cancelar, o tutor escolhe o motivo num modal (`CancelamentoModal`: imprevisto, horário, pet melhorou, outro profissional, outro) e o texto padrão chega ao profissional (WhatsApp e avisos). O motivo é um código de lista fixa (`src/lib/motivos-cancelamento.ts`); texto livre ou código desconhecido vira "Cancelado pelo tutor". Campos digitados por usuários (nomes, pet, local, motivo, serviço) saem sem links (`[link removido]`), sem quebras de linha e com tamanho limitado (`textoSeguro`), porque a mensagem sai do número oficial.
- **Plano:** só envia se o vet **ou** a clínica da consulta tiver a feature `whatsapp_notifications`. Sem plano: registra `ignorado/sem_plano`.
- **Opt-out:** `users.notificar_whatsapp` (padrão ligado), de tutor e de vet, alterado em Perfil > Avisos de consulta. Desligado: quem desligou não recebe nada por WhatsApp (a outra parte continua recebendo). Vet que desligou também não recebe pelo WhatsApp da clínica.
- **Lembretes:** `GET /api/cron/lembretes-whatsapp` (Bearer `CRON_SECRET`; sem segredo configurado, 401), a cada 15 min. No Render quem chama é o cron-job.org (`vercel.json` e `netlify/functions/lembretes-whatsapp.mts` servem a esses hosts). Janela 24h: entre 24h e 2h antes; janela 2h: até o início. Consulta criada depois que a janela abriu não recebe aquele lembrete (a confirmação já cobre).
- **Idempotência e registro:** cada envio grava `whatsapp_envios` com chave única (consulta, evento, destinatário, data+hora da consulta). Repetir o cron não duplica; remarcar muda a referência e libera novos lembretes. Status: `processando` (reservado), `aceito` (gateway enfileirou, falta confirmar), `enviado`, `falhou` (`erro`, `erro_temporario`, `limite_tentativas`, `expirado`) ou `ignorado` (`sem_plano`, `opt_out`, `sem_celular`).
- **Fila no banco:** `whatsapp_envios` é a fila oficial; o texto fica em `mensagem`. O mesmo cron roda `conciliarEnvios()` (`src/server/services/whatsapp-fila.ts`), em lotes de 50, mais antigos primeiro: `aceito` parado há 2 min é conferido no gateway (`GET /messages/:id`) e vira `enviado`, `falhou/erro_temporario` ou, se o gateway perdeu a mensagem (404), é reenviado; `processando` parado há 5 min (app caiu no meio) e `falhou/erro_temporario` são reenviados. Reenvio só enquanto `tentativas` (soma de todas as rodadas) for menor que 3 (senão `limite_tentativas`) e só se o aviso ainda faz sentido: consulta no futuro e, para confirmação, novo agendamento, lembretes e remarcação, consulta ativa com a mesma data/hora do texto (senão `expirado`); lembrete 24h não sai a 2h ou menos da consulta. A linha só muda se continuar como foi lida, então duas execuções do cron não reenviam a mesma mensagem. A chave de idempotência enviada ao gateway é `<id do envio>:<rodada>`.
- **Gateway próprio:** em produção `WHATSAPP_PROVIDER=gateway` aponta (`WHATSAPP_GATEWAY_URL`, `WHATSAPP_GATEWAY_TOKEN`) para o repositório separado `lince-pet-whatsapp-gateway`: uma imagem Docker com gateway + Evolution API, num serviço Render free à parte (memória isolada; deploy do app não derruba a sessão do WhatsApp), mantido acordado pelo UptimeRobot. A sessão da Evolution fica neste mesmo Supabase, no schema `evolution`, dono `evolution_app` (role sem acesso ao `public`; migration `20261022200000_whatsapp_evolution_schema`). O app não lê nem escreve no schema `evolution`.
- **Endereços em produção:** `WHATSAPP_GATEWAY_URL` = `https://lince-pet-whatsapp-gateway.onrender.com` (pareamento, status, health e UptimeRobot partem dela). Job do cron-job.org: `GET https://lincepet.com.br/api/cron/lembretes-whatsapp` a cada 15 min (America/Fortaleza), header `Authorization: Bearer <CRON_SECRET>`; test run 200 em 22/10/2026.
- **Contas provisórias:** o Render do gateway e o cron-job.org estão em contas particulares do responsável técnico. No futuro a LincePet cria a própria conta no cron-job.org e move o gateway para o Render pago da empresa, refazendo variáveis, job, monitores e `WHATSAPP_GATEWAY_URL` (a sessão fica no banco: sem novo pareamento se a `DATABASE_CONNECTION_URI` for mantida).
- **Não bloqueia o fluxo:** envio roda em `after()`, com até 2 tentativas só para erro temporário (429/5xx/rede/timeout de 10 s). Falha do provedor nunca derruba agendamento, cancelamento ou remarcação; a conciliação tenta de novo depois.

### Canais de aviso e Google Agenda

- **Canais por usuário:** tutor e vet escolhem e-mail e WhatsApp em Perfil > Avisos de consulta (`GET/PUT /api/me/notificacoes`, colunas `users.notificar_email` e `users.notificar_whatsapp`, padrão ligado). O aviso só sai pelos canais ligados (`src/server/services/canais-notificacao.ts`). Os avisos in-app (sino) não são desligáveis.
- **Navegador espelha o sino:** todo aviso gravado pelo `create()` de `in-app-notifications.ts` também sai como notificação do navegador (Web Push, `src/server/services/push.ts`) em cada aparelho que o usuário ativou, com link para `/dashboard/{tipo}`. Vale para todos os tipos de usuário e não depende de plano. Ativação por aparelho: interruptor "Notificações no navegador (este aparelho)" no perfil (tutor, vet e prestador em "Avisos de consulta"; clínica em "Avisos") e convite no menu do sino enquanto a permissão não foi pedida. Inscrições em `push_inscricoes` (uma por endpoint; 404/410 do serviço de push apaga). Sem `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` o push fica desligado sem erro; a chave pública chega ao navegador por `GET /api/push/chave-publica`. Falha no push nunca derruba o fluxo. No iPhone o push só funciona com o site instalado na tela inicial (`src/app/manifest.ts`).
- **Avisos ao tutor no sino:** consulta agendada (ao agendar), remarcada (ao remarcar, além do aviso ao vet) e os lembretes, para cobrir o que antes só ia por WhatsApp.
- **Lembretes de consulta (só para o tutor):** 24h e 2h antes, pelo mesmo cron do WhatsApp (`processarLembretes` em `whatsapp-lembretes.ts`), sem depender de plano. Os dois saem no sino e no navegador; por e-mail só o de 24h ("Sua consulta é amanhã", `src/server/emails/lembrete_consulta.ts`, respeita `notificar_email`). Envio único por (consulta, evento, data+hora) em `avisos_lembrete`; remarcar libera lembretes novos. O WhatsApp segue as regras próprias. Para exame, o texto vira "Seu exame é amanhã/daqui a pouco", com os exames, "pagamento na clínica" e o preparo de cada exame.
- **WhatsApp fora do ar:** com o número central banido (23/10/2026), produção roda sem `WHATSAPP_PROVIDER` (padrão `log`); nenhum código de WhatsApp foi removido.
- **E-mail desligável por completo:** como o código de início da consulta ia só por e-mail, ele aparece no painel do tutor (`codigo_inicio` em `GET /api/agendamentos`) nas consultas futuras não canceladas e não iniciadas.
- **Google Agenda = conexão:** o canal fica ativo enquanto a conta Google estiver conectada; não há interruptor separado. Tutor e vet conectam a própria conta (`/api/google/calendar/auth`). Para o vet, conectar exige plano Pro (trava no front).
- **Sincronização do evento:** criar consulta insere o evento na agenda de cada participante conectado; remarcar atualiza o evento (se sumiu no Google, cria outro); cancelar (pelo tutor ou por bloqueio de agenda) apaga o evento. O id fica em `agendamento_google_eventos` (consulta x usuário). Falha do Google nunca derruba o fluxo; 401/403 desliga a integração do usuário.
- **Conexão presa à sessão:** o callback (`/api/google/calendar/callback`) só grava os tokens se o usuário logado no navegador for o mesmo do `state`; senão redireciona com `google_calendar_error=session_mismatch`. `redirect_to` absoluto só vale para a origem do app (`FRONTEND_BASE_URL`/`NEXT_PUBLIC_APP_URL`); outra origem é ignorada.
- **Desconectar:** `POST /api/google/calendar/disconnect` revoga o token no Google (melhor esforço) e limpa as credenciais. Para de criar eventos novos; não apaga consultas da plataforma nem os eventos já criados no Google.

### Prestadores de serviço pet

- **Conta genérica:** tosador, passeador, adestrador, pet sitter e os próximos tipos usam a mesma conta `prestador` (`user_type = prestador`). O tipo vem do catálogo `tipos_servico` (`slug`, `nome`, `modalidade`), populado pelo seed; tipo novo = linha nova no catálogo, sem código novo. Cadastro em `/signup/prestador`, onboarding em 3 passos (onde atende, serviços e preços, apresentação e grade semanal), painel em `/dashboard/prestador`, perfil público em `/profissionais/:id`.
- **Um tipo por prestador:** quem faz dois serviços diferentes cria duas contas. Dentro do tipo, o prestador cadastra vários serviços (`servicos_oferecidos`), cada um com preço e, na modalidade duração, minutos.
- **Sem dados de veterinário:** sem CRMV, especialidade, consulta online, prontuário, registro clínico ou anotação privada. A tela e as rotas são próprias (`src/server/services/prestadores.ts` e `pedidos-prestador.ts`).
- **Busca:** aba "Profissionais" em `/explorar` com filtro por tipo (`GET /api/prestadores/search?tipo=`); só aparece quem concluiu o onboarding e está ativo.
- **Pedido = `Agendamento`:** com `prestador_id` e `servico_oferecido_id`, sem veterinário. Todo pedido tem `inicio_em`/`fim_em` (UTC; regras de dia/horário em `America/Sao_Paulo`).
  - **Duração** (banho, tosa, passeio, adestramento): fim = início + duração do serviço; precisa caber na grade do dia.
  - **Período** (hospedagem / pet sitter): entrada e saída em dias diferentes, até 30 dias; preço = diária × número de dias (arredondado para cima). Entrada e saída precisam cair dentro da grade dos respectivos dias.
- **Sem sobreposição:** pedidos `pendente`, `confirmado` ou `em andamento` ocupam a agenda; outro pedido que sobreponha o período recebe 409. A checagem é refeita na transação.
- **Local:** o tutor escolhe domicílio (endereço do tutor) ou local do profissional, só entre os que o prestador atende.
- **Aceite obrigatório:** o pedido nasce `pendente`; o prestador aceita (`confirmado`) ou recusa (`cancelado`, com motivo opcional). Remarcar pelo tutor volta o pedido para `pendente`.
- **Código de início:** o tutor só vê o código depois do aceite. O prestador digita o código para iniciar (`em andamento`, até 5 tentativas) e depois conclui (`realizado`); o tutor pode avaliar o serviço concluído.
- **Bloqueio de agenda do prestador:** mesmo modelo de `bloqueios_agenda` (dia inteiro ou horários, cada horário bloqueia 1h). Diferente do vet, bloqueio que atinge pedido ativo é recusado com 409 e a lista de conflitos: o prestador recusa ou combina a remarcação antes.
- **Limite do plano:** o prestador começa no plano `free` (10 pedidos/mês) e pode assinar o `pro` (ilimitado) pelo mesmo fluxo Asaas (`/api/assinaturas`, referência `prestador:<id>`). Pedido criado conta no mês; recusa ou cancelamento devolve a cota. Cancelar ou atrasar a assinatura volta para `free`.
- **Avisos:** os mesmos canais da consulta (in-app, e-mail, WhatsApp e Google Agenda) com texto de serviço ("Novo pedido de Banho e tosa", sem "Dr(a)." nem "consulta"). WhatsApp do prestador depende do plano dele ter `whatsapp_notifications`.

### Encaminhamento de pet

- **Quem envia:** só o vet ou a clínica da consulta (`POST /api/agendamentos/:id/encaminhamentos`), a partir do início do atendimento (mesma janela do registro clínico); consulta cancelada não encaminha. O campo de encaminhamento em texto livre do registro clínico continua.
- **Destino:** outra clínica, outro veterinário ou um prestador (`destino_tipo` = `clinica`, `veterinario` ou `prestador`), ativo na plataforma. Não pode encaminhar para si mesmo. Motivo obrigatório (3 a 2000 caracteres) e urgência `rotina` (padrão) ou `prioritario`.
- **Sem duplicado:** já existindo encaminhamento `enviado` da mesma consulta para o mesmo destino, responde 409.
- **Status:** nasce `enviado`; o destino aceita (`aceito`) ou recusa (`recusado`, com motivo de pelo menos 3 caracteres). Só o destino responde e só uma vez. Painel "Encaminhamentos recebidos" nos dashboards de vet, clínica e prestador (`/api/encaminhamentos/recebidos`).
- **Prontuário:** enquanto o encaminhamento está `enviado` ou `aceito`, o destino (inclusive prestador) vê o prontuário do pet. Encaminhamentos aceitos aparecem no prontuário (origem, destino, motivo e consulta marcada).
- **Quem marca é o tutor** (decisão da dona do produto): depois do aceite, o tutor vê "Agendar com X" no painel e agenda pela tela normal do destino (`?encaminhamento=&pet=`), com o pet já escolhido e a própria agenda do dia ao lado da agenda do destino. A marcação segue as regras normais do destino (grade, bloqueios, limite do plano, aceite do prestador).
- **Vínculo:** `encaminhamento_id` em `POST /api/agendamentos` e no pedido de prestador. Só vale para encaminhamento `aceito` do próprio tutor, para o mesmo pet e o mesmo destino, e sem outra marcação ativa (409). A consulta criada fica em `agendamento_destino_id`.
- **Avisos:** novo encaminhamento avisa destino e tutor (sino e e-mail); aceite e recusa avisam tutor e origem (sino e e-mail) e o tutor por WhatsApp (plano da consulta de origem, mesmas regras de opt-out). Falha de aviso nunca bloqueia o fluxo.

### Painel admin e aprovações

- **Admin da Lince:** `users.is_admin = 1` (padrão 0). Não há cadastro de admin pela tela: o primeiro é promovido por `UPDATE users SET is_admin = 1 WHERE id = '<id>'`, só com confirmação do dono do produto. `requireAdmin` (`src/server/auth/session.ts`): sem login 401, não admin 403. Menu "Admin" no cabeçalho só para admin; `/admin/aprovacoes` sem login vai para o login.
- **O que o admin aprova:** o CRMV do vet (`veterinarios.crmv_status` = `pendente` | `aprovado` | `reprovado`, `crmv_motivo`) e o responsável técnico da clínica (`clinicas.rt_nome`, `rt_crmv` no formato `12345-SP`, `rt_status`, `rt_motivo`). Rotas `GET /api/admin/aprovacoes` (só pendentes), `POST /api/admin/aprovacoes/veterinarios/:id` e `.../clinicas/:id`. Reprovar exige motivo. Vets ativos na migração `20261023130000_admin_aprovacoes` entraram como aprovados.
- **Volta para análise:** vet novo nasce `pendente`; trocar o CRMV (vet) ou o RT (clínica) volta para `pendente` e limpa o motivo.
- **Travas:** vet não aprovado fica fora da busca e `POST /api/agendamentos` com ele responde 400. Clínica com RT não aprovado não mostra exames ao público (o cadastro de exames e preços já funciona).
- **Avisos:** aprovar ou reprovar avisa o usuário no sino, no navegador e por e-mail (com o motivo). Os perfis do vet e da clínica mostram "Em análise", "Aprovado" ou "Reprovado: motivo".

### Clínica de exames

- **Conta:** módulo da própria conta de clínica (`clinicas.exames_ativo`); laboratório = clínica sem vets com o módulo ligado. Sem tipo de usuário novo.
- **Entrada no cadastro:** o card "Clínica e laboratório" em `/signup` leva ao mesmo `/signup/clinica` para clínica veterinária, clínica de exames e laboratório. O menu e a introdução do formulário informam que exames exigem plano pago e RT aprovado; laboratório não precisa de veterinários vinculados.
- **Plano:** só planos pagos de clínica ligam o módulo, com limite de exames agendados por mês (`LIMITE_EXAMES_MES` em `assinatura-regras.ts`: `starter` 100, `clinic` 300, `clinic_pro` ilimitado; feature `exames` no catálogo de planos). Sem plano, ligar responde 403. Inadimplência ou cancelamento (volta ao plano padrão) mantém os exames marcados e bloqueia novos (403). Limite do mês atingido: 403.
- **Visível ao público** só com módulo ligado, RT aprovado e plano com exames: aba "Exames" em `/explorar` (filtro por nome e cidade) e seção "Exames" no perfil público da clínica, sempre com "pagamento na clínica".
- **Catálogo:** `exames_oferecidos` (nome, descrição, preparo, preço, `duracao_min`, `capacidade` simultânea, ativo); preço, duração e capacidade maiores que zero. Exame com agendamento futuro só é desativado, não apagado. Combos (`combos_exame` + `combo_exame_itens`) com nome e preço próprios e pelo menos 2 exames ativos da mesma clínica; combo com exame desativado sai do ar.
- **Agendamento:** `Agendamento` com `tipo_consulta = 'exame'`, `clinica_id`, sem vet, já nasce `confirmado`. Itens em `agendamento_exames` com cópia de nome, preparo, preço e duração. Duração = soma dos exames; total = soma dos preços ou o preço do combo. Pagamento sempre na clínica.
- **Disponibilidade:** o horário cabe no `horarios_funcionamento` da clínica, respeita os bloqueios de agenda e, para cada exame, os agendamentos ativos sobrepostos ficam abaixo da `capacidade`. A checagem é refeita na transação com `pg_advisory_xact_lock`; sem vaga, 409.
- **Encaminhamento:** opcional (`encaminhamento_id`): só vale aceito, do mesmo pet e tutor, com a clínica como destino.
- **Ações:** o tutor cancela e remarca pelas mesmas regras da consulta (remarcar mantém os exames e checa a capacidade ignorando o próprio agendamento). A clínica marca "realizado" a partir do horário do exame e cancela com motivo (o tutor é avisado).
- **Avisos:** agendado, remarcado e cancelado vão para tutor e clínica (sino, navegador e e-mail) e para a agenda Google do tutor. Lembretes 24h/2h com preparo (ver "Canais de aviso").
- **Laudo:** só depois de o exame estar `realizado`, a clínica envia um PDF (até 10 MB, conferido pela assinatura `%PDF-`; `POST /api/clinicas/exames/agenda/:id/laudo`, campo `laudo`). Um laudo por exame (`laudos_exame`); enviar de novo substitui e apaga o arquivo anterior. Avisa o tutor e o vet ou clínica de origem do encaminhamento ("Laudo disponível").
- **Acesso ao laudo:** quem vê o prontuário do pet (tutor dono, clínica do exame, vets com consulta ou encaminhamento do pet); outro usuário recebe 403. `GET /api/exames/agendamentos/:id/laudo` devolve uma URL assinada de 60 s. O laudo aparece no prontuário e no painel do tutor ("Ver laudo").
- **Storage do laudo:** bucket privado `lincepet-laudos` (`SUPABASE_LAUDOS_BUCKET`; criado via MCP em 23/10/2026, migração `storage_bucket_lincepet_laudos`; no mesmo dia as migrations `admin_aprovacoes` e `clinica_exames` foram aplicadas via MCP em produção, idempotentes, e o `prisma migrate deploy` do próximo start as registra), só `application/pdf`, 10 MB, sem policies em `storage.objects`; só o backend escreve e assina, com `SUPABASE_SERVICE_ROLE_KEY`. Caminho `clinicas/{clinicaId}/{agendamentoId}/{uuid}.pdf`, `x-upsert: false`. Dev e e2e usam um driver local (`LAUDOS_STORAGE_DIR` + `LAUDOS_STORAGE_SECRET`, link HMAC em `/api/exames/laudos/local`), proibido em produção.
- **Fora desta versão:** pagamento online, validação automática do CRMV, coleta domiciliar, resultado estruturado e pedido de exame entre clínicas sem consulta.

### Storage de imagens

- **Onde:** Supabase Storage, bucket público `lincepet-media` (criado via MCP, migração `storage_bucket_lincepet_media`): `file_size_limit` 5 MB, `allowed_mime_types = {image/webp}`, nenhuma policy em `storage.objects`. Leitura é pública; só o backend escreve, com `SUPABASE_SERVICE_ROLE_KEY` (nunca `NEXT_PUBLIC_*`). Só fotos de exibição pública (perfil, capa, local, pet); documento privado não vai para este bucket.
- **Caminhos por dono** (id do banco/sessão, validado como UUID; nada do cliente entra no caminho): `veterinarios/{vetId}/perfil|uploads/`, `veterinarios/{vetId}/locais/{enderecoId}/`, `clinicas/{clinicaId}/perfil|capa/`, `pets/{petId}/`, `tutores/{userId}/`, `prestadores/{prestadorId}/`, sempre `{uuid}.webp`. Fotos antigas migradas ficam em `legado/{caminho-original}.webp` (o bucket só aceita WebP, então passam pelo mesmo `sharp`).
- **Validação:** as rotas checam tamanho (5 MB) e extensão; o `sharp` decodifica o conteúdo de verdade (jpeg, png, webp ou gif; ignora o MIME do navegador), corrige a rotação, limita a 1600px e grava WebP q82 sem metadados (EXIF/GPS). Vazio, corrompido, SVG ou não-imagem: 400 "Arquivo de imagem inválido". Upload com `x-upsert: false` (nunca sobrescreve).
- **Consistência:** `confirmarUpload` grava a URL no banco; se a gravação falhar, apaga o objeto recém-enviado. Se der certo, apaga a foto anterior **só** se for do nosso bucket, estiver na pasta do mesmo dono do upload novo (`pasta/donoId/`, o que já exclui `legado/`) e não for referenciada em outra coluna (ex.: `users.profile_pic`). Como a URL anterior pode ter vindo do cliente, apontar a própria foto para a de outra pessoa não apaga a dela. URLs da AWS/CloudFront e externas nunca são apagadas.
- **Cadastro de veterinário:** cria o usuário primeiro e depois envia a foto para a pasta do novo veterinário; falha na foto não impede o cadastro.
- **URL de foto vinda do cliente:** campos JSON/form que recebem URL (`foto_url` do pet, `fotoUrl` do passo 4 da clínica) só aceitam URL do nosso bucket (`fotoDoCliente` -> `chaveDoBucket`) ou vazio; qualquer outra (site externo, outro projeto, AWS, `..`) responde 400 sem gravar. A foto nova entra sempre pelo upload.
- **Erros:** log com status, chave e `sb-request-id`; nunca headers ou chave.
- **Fotos antigas (AWS):** inventário via MCP em 15/10/2026: só `pets.foto_url` tinha URL antiga (1 registro, CloudFront). Migração manual: baixar, validar, converter para WebP, subir em `legado/` com `x-upsert: false`, conferir sha256 do WebP pela URL pública e só então `UPDATE pets SET foto_url = '<nova>' WHERE id = '<id>' AND foto_url = '<antiga>'` com confirmação. Nada é apagado da AWS. Inventário para repetir:

```sql
SELECT tabela, coluna, classe, count(*) FROM (
  SELECT 'users' tabela, 'profile_pic' coluna, profile_pic url FROM users
  UNION ALL SELECT 'veterinarios', 'foto_url', foto_url FROM veterinarios
  UNION ALL SELECT 'clinicas', 'foto_perfil', foto_perfil FROM clinicas
  UNION ALL SELECT 'clinicas', 'foto_capa', foto_capa FROM clinicas
  UNION ALL SELECT 'prestadores', 'foto_url', foto_url FROM prestadores
  UNION ALL SELECT 'veterinario_enderecos', 'foto_url', foto_url FROM veterinario_enderecos
  UNION ALL SELECT 'pets', 'foto_url', foto_url FROM pets
  UNION ALL SELECT 'planos', 'image', image FROM planos
) t CROSS JOIN LATERAL (SELECT CASE
  WHEN url IS NULL OR url = '' THEN 'vazio'
  WHEN url ILIKE '%amazonaws.com%' THEN 's3'
  WHEN url ILIKE '%cloudfront.net%' THEN 'cloudfront'
  WHEN url ILIKE '%supabase.co/storage/%' THEN 'supabase'
  ELSE 'externa' END classe) c
GROUP BY 1, 2, 3 ORDER BY 1, 2, 3;
```

- **Pendência conhecida:** algumas rotas ainda aceitam URL de foto vinda do cliente (`foto_url` de pet, `fotoUrl` de endereço e do step4 da clínica, usada pelo fluxo de `upload-generic`). Não abre escrita no bucket, mas permite gravar URL externa.
- **Variáveis:** `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (service_role legada ou `sb_secret_...`), `SUPABASE_STORAGE_BUCKET=lincepet-media`. As antigas `AWS_*`, `S3_*` e `NEXT_PUBLIC_CDN_BASE_URL` não são mais usadas. Os `remotePatterns` da AWS/CloudFront em `next.config.ts` saem quando o inventário não tiver mais URL da AWS.

## Testes

- `npm test`: unitários (`tests/server`).
- `npm run test:coverage`: unitários com cobertura de `src/server/services`. Falha se algum serviço ficar abaixo de 95% de linhas, statements ou funções (por arquivo). Os testes de cobertura por serviço ficam em `tests/server/cobertura/`; Prisma e integrações externas (Asaas, Supabase Storage via `fetch`, Resend, WhatsApp, Google) sempre mockados. O storage usa o `sharp` real sobre imagens geradas no teste; as rotas de upload são cobertas em `tests/server/upload-rotas.test.ts`.
- `npm run test:mutation`: testes de mutação (StrykerJS + vitest-runner, config em `stryker.config.json`) nos serviços críticos — assinatura/Asaas, limite de equipe/vínculos, bloqueios, pedidos de prestador, encaminhamentos e storage de imagens. Mede se os testes falham quando o código é alterado (cobertura só mede execução). Incremental (`reports/stryker-incremental.json`), relatório em `reports/mutation/index.html`. Meta: mutation score ≥ 80% por arquivo. Lento (dezenas de minutos na primeira execução): rodar sob demanda ou no CI noturno, não a cada commit.
- `npm run test:e2e`: Playwright (`e2e/`, detalhes no README).
  - **Só banco local:** o `globalSetup` aborta se `DATABASE_URL` não for `127.0.0.1:5433`/`localhost:5433`, roda o seed e cancela consultas futuras ativas de pets criados pelos testes. Nunca roda contra produção.
  - **Sem envio real:** o servidor do teste usa `MAIL_DRIVER=log`, `WHATSAPP_PROVIDER=log` sem gateway, um `CRON_SECRET` aleatório e chaves VAPID geradas na hora (a inscrição real no serviço de push fica nos unitários). Não há e2e de WhatsApp: um envio real de teste fez o WhatsApp derrubar a sessão do número central (23/10/2026), então o WhatsApp fica coberto só pelos unitários.
  - **Pela tela:** a ação testada é feita pela interface; a API só entra em passos "invasão (fora da tela)" e o banco só confere o resultado.
- `npm run test:contract`: compara Adonis x Next quando `CONTRACT_ADONIS_URL` e `CONTRACT_NEXT_URL` estão definidos.
